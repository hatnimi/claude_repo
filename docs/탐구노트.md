# 탐구노트: TTS의 동음이의어 장단음 처리

> 이 노트는 **직접 실행하면서 채우는** 기록장이다. 실행 결과로 정답이 정해지는 칸은 실제 결과로 채웠다.
> `( )`로 남은 칸은 직접 듣고 느낀 점처럼 **내가 판단해서 써야 하는** 칸이다.
> 면접에서는 외운 답보다 "직접 돌려 보니 이랬다"는 말이 힘이 있다.

## 1. 문제를 어떻게 발견했나 (동기)
- 시작 질문: TTS로 "눈에 눈이 들어갔다"를 읽히면 두 '눈'을 다르게 읽을까?
- 직접 들어 본 결과: ( )
- 문제의 구조: TTS 입력은 **글자**뿐이다. 장단은 글자에 드러나지 않고 **의미**에 따라 정해진다.
  따라서 "의미 판별 → 음성 생성"의 두 단계가 모두 필요하다.

## 2. 배경 지식
- **표준 발음법 제6항**: 모음의 장단을 구별하여 발음하되, 단어의 첫음절에서만 긴소리가 나타난다.
  - 눈보라[눈ː보라] / 첫눈[천눈], 말씨[말ː씨] / 거짓말[거ː진말]
  - 그래서 코드에서 **형태소가 어절 첫머리일 때만** 장음을 적용했다 (`morph.py`의 `word_initial`).
- **현실의 한계**: 현대 서울말 화자, 특히 젊은 세대는 장단을 거의 구별하지 않는다는 연구가 많다.
  → "표준 발음을 지키는 TTS"와 "자연스럽게 들리는 TTS"가 다를 수 있다. 이 탐구의 목표는 표준 발음 쪽이다.
- **VITS 구조**: 텍스트 인코더 → **duration predictor**(토큰마다 몇 프레임 낼지) → 정렬 → flow → HiFi-GAN 디코더.
  장단은 결국 '몇 프레임'의 문제이므로 duration predictor의 출력이 개입하기 좋은 지점이다.

## 3. 방법 1: 형태소 분석기 + Gemini + 상용 TTS
### 3-1. 형태소 분석기를 쓴 이유
- '눈이', '눈을', '눈에'처럼 조사가 붙은 어절에서 명사 '눈'만 정확히 떼어 내야 한다.
- 형태소 분석기가 **못 하는 것**: `눈/NNG`(目)과 `눈/NNG`(雪)은 품사까지 같아서 구별하지 못한다.
- 직접 확인: `올해 첫눈은 눈이 부시게 하얗게 내렸다.` → Kiwi 결과
  `올해/NNG + 첫/MM + 눈/NNG + 은/JX + 눈/NNG + 이/JKS + 부시/VA + 게/EC + ...`
  - '첫눈'이 `첫/MM + 눈/NNG`으로 나뉜다. 그래서 '눈'만 떼어 내 후보로 잡을 수 있다.
  - 하지만 이 '눈'은 어절('첫눈은')의 첫머리가 아니다. 그래서 표준 발음법 제6항에 따라 장음 대상에서 뺐다.
  - 두 '눈'은 모두 `NNG`이다. 형태소 분석기만으로는 雪/目을 구별할 수 없다는 것이 확인된다.

### 3-2. Gemini를 쓴 이유와 설계
- 의미 판별에는 문장 전체의 문맥이 필요하다. 예) "눈이 부시게"는 '하얗게 내렸다'가 옆에 있어도 目.
- 설계 결정
  - 후보 의미를 **사전에서 골라 주고** 그중에서만 선택하게 했다 → 사전에 없는 답(환각)을 막는다.
  - `temperature=0`, JSON 응답 강제 → 결과가 재현되고 자동으로 채점할 수 있다.
  - 응답을 `outputs/gemini_cache.json`에 저장 → 판단 근거(reason)를 나중에 확인할 수 있다.
- 결과 (`outputs/disambiguation.md`)

| 방법 | 의미 정확도 | 장단 정확도 |
|---|---|---|
| baseline (항상 짧은 의미) | 56% (14/25) | 60% (15/25) |
| Gemini (`gemini-3.6-flash`) | **100% (25/25)** | **100% (25/25)** |

- Gemini가 틀린 문장: **없음.** 25개를 모두 맞혔다.
- Gemini가 댄 근거 중 인상적인 것 (`outputs/gemini_cache.json`의 `_원본_응답`에 원문 보관)
  - "올해 첫눈은 **눈이 부시게** 하얗게 내렸다" → 目: "하얗게 내린 눈으로 인해 부심을 느끼는 신체 기관"
    - 옆에 '하얗게 내렸다'라는 雪 단서가 있는데도 '부시다'와의 관계로 目을 골랐다.
  - "이 배는 저 배보다 두 **배**나 크다" → 倍: "크기의 수량적 곱절(두 배)"
  - "아버지와 아들, 두 **부자**는 마침내 **부자**가 되었다" → 앞은 父子("앞서 언급된 아버지와 아들"), 뒤는 富者
- 비교: baseline(항상 짧은 의미)은 의미 56%(14/25), 장단 60%(15/25)였다.
  - 정답이 장음인 11개 중 baseline은 10개를 틀렸다. 맞힌 1개는 사전에 의미가 하나뿐인 '눈보라'다.
- 의미는 틀렸는데 장단은 맞은 경우가 있었나? → **baseline에서 1건.**
  - "올해 **첫눈**은 ..."의 '눈'은 정답이 雪인데 baseline은 目으로 골랐다(의미 X).
  - 그런데 이 '눈'은 단어 중간이라 雪이어도 짧게 읽는다. 그래서 장단은 맞았다(장단 O).
  - 그래서 baseline의 장단 정확도(60%)가 의미 정확도(56%)보다 높다.
  - **"의미를 틀려도 소리는 맞을 수 있다"** → 장단음 문제에서는 의미 정확도와 장단 정확도를 따로 재야 한다.

### 3-4. 시행착오 기록 (문제 해결 과정)
| 문제 | 원인 | 해결 |
|---|---|---|
| `404 NOT_FOUND` | 처음 쓴 `gemini-2.5-flash`가 신규 사용자에게 더 이상 제공되지 않음 | 오류 메시지가 권한 모델로 교체하고, 노트북에서 **쓸 수 있는 모델 목록을 조회해 고르도록** 바꿈 |
| `503 UNAVAILABLE`이 모델을 바꿔도 반복 | 무료 등급 요청은 서버가 붐빌 때 먼저 거절됨. 12문장을 12번 따로 요청해서 한 번만 거절돼도 실패 | ① 잠시 기다렸다 자동 재시도 ② **12문장을 한 번의 요청으로 묶음** ③ 짧은 시험('안녕')은 성공하는데 실험만 실패해서, 두 요청의 차이(JSON 응답 모드)를 없앰 → `gemini-3.6-flash`로 성공 |
| 실패하면 원인과 무관한 `FileNotFoundError`만 보임 | 결과 파일을 모든 단계가 끝난 뒤에만 썼음 | 단계마다 결과를 저장하고, 실패하면 원인과 해결 방법을 결과 파일에 남김 |

- 배운 점: 외부 API는 **모델 이름이 바뀌고 서버가 붐빌 수 있다.** 그래서 ① 결과를 저장해 다시 묻지 않고 ② 요청 횟수를 줄이고 ③ 실패 원인을 바로 보이게 만드는 것이 중요했다.

### 3-5. 상용 TTS에 적용
- SSML `<prosody rate="55%">눈</prosody>이`: 장음 음절만 느리게 읽힌다.
- SSML을 지원하지 않는 TTS(gTTS)는 철자를 바꾼다: 눈 → 누운.
  이중모음은 뒤쪽 단모음을 늘린다: 과(ㅘ=ㅗ+ㅏ) → 과아.
- 관찰: 실제로 길게 들렸나? 부자연스러운 점은? ( )
- 한계: 상용 TTS는 내부를 볼 수 없어서 **입력만** 바꿀 수 있다. 음절 하나를 SSML로 감싸면 단어 중간에 경계가 생긴다.
  그래서 운율이 끊기거나 '누-운'처럼 두 음절로 들릴 수 있다.

## 4. 방법 2: VITS 텐서에 직접 개입
### 4-1. 아이디어
```python
def hook(module, inputs, output):          # output = log_duration, 모양 (1, 1, 토큰 수)
    return output + log_w                  # 장음 모음 토큰 위치만 log(w), 나머지는 0
model.duration_predictor.register_forward_hook(hook)
```
- **왜 log 공간에서 더하나?** 모델이 `duration = ceil(exp(log_duration))`로 계산한다.
  `exp(a + log w) = w · exp(a)`이므로 더하기 한 번이 곱하기 w가 된다.
- **왜 speaking_rate를 쓰지 않았나?** speaking_rate는 문장 전체 속도를 바꾼다. 우리는 모음 하나만 늘려야 한다.
- **왜 blank 토큰도 늘렸나?** MMS 토크나이저는 글자 사이에 blank(`_`)를 끼운다(`_ n _ u _ n _`).
  모음 소리가 blank 쪽까지 이어지는 경우가 많아서 모음 토큰과 바로 뒤 blank를 같이 늘렸다.
  - 실험해 볼 것: 모음 토큰만 늘렸을 때와 비교 ( )
- **공정한 비교**: VITS의 duration predictor는 난수를 쓴다. 그래서 기본 음성과 수정 음성을 같은 seed로 생성했다.
- **입력이 로마자인 이유**: `mms-tts-kor`는 한글을 uroman으로 로마자화한 입력으로 학습됐다.
  그래서 한 음절씩 로마자로 바꾸면서 "이 로마자 글자는 몇 번째 한글 음절에서 왔는지"를 기록해 두었다(`romanize`).

## 5. 멜 스펙트로그램 비교
- 멜 스펙트로그램: 가로축은 시간, 세로축은 사람 귀의 감도에 맞춘 주파수(멜 척도), 색은 에너지.
- 무엇을 봐야 하나: 장음 음절 구간(하늘색)에서 모음의 **포먼트 띠**(가로 줄무늬)가 옆으로 더 길게 이어지는가.
- **VITS**: duration을 알기 때문에 음절 구간을 정확히 표시할 수 있다.
- **상용 TTS**: 정렬 정보가 없다. 그래서 DTW로 두 음성을 맞춰 "기본 음성의 각 순간이 몇 배로 늘어났는지"를 그렸다.
  - DTW 검증: 합성 신호에서 한 구간만 2배로 늘렸을 때 그 구간의 평균 배율은 2.07, 나머지는 0.98이었다.
  - 주의: 소리가 일정한 구간 안에서는 DTW가 늘어난 위치를 정확히 짚지 못하고 한쪽에 몰아서 표시한다.
    그래서 곡선의 모양보다 **구간 평균**으로 해석해야 한다.

## 7. 한계와 후속 탐구
- 사전에 있는 단어만 처리한다 → 표준국어대사전 전체에서 장단음 동음이의어를 자동으로 추출할 수 있을까?
- 용언의 장단(감ː다/감다, 묻ː다/묻다)과 활용 시 단음화(감ː다 → 감아[가마])는 다루지 못했다.
- 길이만 바꿨다. 실제 장음에는 음높이나 강세 변화가 함께 나타날 수 있다.
- 평가가 내 귀와 구간 길이뿐이다 → 여러 사람에게 들려주고 "어느 쪽이 雪으로 들리나" 청취 실험을 할 수 있다.
- 근본적인 해결: 장단 표시(ː)를 입력에 넣은 데이터로 TTS를 학습시키는 방법.

## 면접 예상 질문 (내 말로 답해 보기)
1. 형태소 분석기만으로는 왜 안 되나? → 품사가 같은 동음이의어는 구별하지 못한다. 문맥 이해는 LLM이 맡았다.
2. Gemini가 틀리면 어떻게 하나? → 후보를 사전 안으로 제한하고, 정답 데이터로 정확도를 쟀다. 기본 문장에서는 틀린 사례가 없었다. 그래서 **단서를 약하게 만든 어려운 문장**으로 다시 시험했다(3-3절).
3. 텐서에 개입했다는 게 구체적으로 무슨 뜻인가? → duration predictor 출력에 hook을 걸고 log 공간에서 더했다.
4. 왜 곱하지 않고 더했나? → 4-1 참고.
5. 장음이 제대로 됐는지 어떻게 확인했나? → duration 프레임 수, 멜 스펙트로그램, DTW, 직접 청취.
6. 두 방법 중 무엇이 더 나은가? → 상황에 따라 다르다. ( )
7. 다시 한다면 무엇을 바꾸겠나? → 7번 참고 중 하나를 골라 구체적으로.

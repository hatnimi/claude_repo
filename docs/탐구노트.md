## 핵심 결과 한눈에 보기

### ① 문맥 판별 (Gemini `gemini-3.6-flash`)
| 문장 | baseline (의미 / 장단) | Gemini (의미 / 장단) |
|---|---|---|
| 기본 12문장 (25개 단어) | 56% / 60% | **100% / 100%** |
| 어려운 12문장 (20개 단어) | 45% / 55% | **100% / 100%** |

### ② VITS 결과 (가중치 1.8)
| 장음 음절 | 기본 | 개입 후 | 배율 |
|---|---|---|---|
| 눈(雪) | 240ms | 304ms | 1.27 |
| 말(言) | 144ms | 176ms | 1.22 |
| 밤(栗) | 208ms | 240ms | 1.15 |
| 사(謝) | 160ms | 208ms | 1.30 |

- **지정한 모음과 바로 뒤 blank만 정확히 늘어났고, 나머지 토큰은 그대로였다.**
- 그런데 1.8배로 했는데도 음절은 1.15~1.3배만 늘었다. 이유는 두 가지다.
  1. 음절 안의 자음은 늘리지 않았다.
  2. 모음에 원래 배정된 시간이 2프레임(32ms)뿐이었다. 그래서 곱해도 늘어나는 양이 작았다.
- '말', '밤'은 문장 전체가 겨우 0.032초 길어졌다. 들을 때 "단어에 따라 차이가 별로 없었다"고 느낀 것이 숫자로 확인됐다.

### ③ 그림 분석으로 확인한 것 (멜 스펙트로그램 + DTW)
- **'사과' 가설이 확인됐다.**
  - gTTS에서 한 음절 단어(눈, 말, 밤)는 늘어난 곳이 한 군데이고, 문장이 0.085~0.107초 길어졌다.
  - '사과'는 늘어난 곳이 **두 군데**이고, 문장이 **0.235초** 길어졌다.
  - 모음 하나가 길어진 게 아니라, 음절이 하나 더 생긴 것처럼 단어의 리듬이 바뀐 것이다.
- **VITS '눈'**: 장음 구간에서 DTW 배율이 1.8로 솟았다. 설정한 가중치와 같은 값이다.

### ④ 결론
- 직접 들어 보니 **gTTS + 철자 변형이 더 자연스러웠다.** VITS는 원하는 모음만 정확히 늘렸지만 기본 음질이 낮았다.
- **정밀하게 제어할 수 있는 방법(VITS)은 음질이 낮고, 음질이 좋은 방법(gTTS)은 제어가 거칠다.**
- 자세한 내용: 판별은 3-2·3-3절, VITS는 4-2절, 그림 분석은 5-5절, 비교는 6절

## 1. 문제를 어떻게 발견했나 (동기)
- 시작 질문: TTS로 "눈에 눈이 들어갔다"를 읽히면 두 '눈'을 다르게 읽을까?
- 직접 들어 본 결과: ( )
- 문제의 구조
  - TTS의 입력은 **글자**뿐이다.
  - 장단은 글자에 드러나지 않고 **의미**에 따라 정해진다.
  - 그래서 "의미 판별"과 "음성 생성"의 두 단계가 모두 필요하다.

## 2. 배경 지식
- **표준 발음법 제6항**: 모음의 장단을 구별해 발음한다. 단, 긴소리는 **단어의 첫음절에서만** 나타난다.
  - 눈보라[눈ː보라] / 첫눈[천눈]
  - 말씨[말ː씨] / 거짓말[거ː진말]
  - 그래서 코드에서는 **형태소가 어절 첫머리일 때만** 장음을 적용했다(`src/morph.py`의 `word_initial`).
- **현실의 한계**: 현대 서울말 화자, 특히 젊은 세대는 장단을 거의 구별하지 않는다는 연구가 많다.
  - 그래서 "표준 발음을 지키는 TTS"와 "자연스럽게 들리는 TTS"가 다를 수 있다.
  - 이 탐구의 목표는 표준 발음 쪽이다.
- **VITS 구조**: 텍스트 인코더 → **duration predictor**(토큰마다 몇 프레임 소리를 낼지) → 정렬 → flow → HiFi-GAN 디코더
  - 장단은 결국 '몇 프레임'의 문제다. 그래서 duration predictor의 출력이 개입하기 좋은 지점이다.

## 3. 방법 1: 형태소 분석기 + Gemini + 상용 TTS

### 3-1. 형태소 분석기(Kiwi)를 쓴 이유
- '눈이', '눈을', '눈에'처럼 조사가 붙은 어절에서 명사 '눈'만 정확히 떼어 내야 한다.
- 직접 확인: `올해 첫눈은 눈이 부시게 하얗게 내렸다.`의 Kiwi 결과
  ```
  올해/NNG + 첫/MM + 눈/NNG + 은/JX + 눈/NNG + 이/JKS + 부시/VA + 게/EC + ...
  ```
  - '첫눈'이 `첫/MM + 눈/NNG`으로 나뉜다. 그래서 '눈'만 떼어 내 후보로 잡을 수 있다.
  - 하지만 이 '눈'은 어절('첫눈은')의 첫머리가 아니다. 그래서 표준 발음법 제6항에 따라 장음 대상에서 뺐다.
  - 두 '눈'은 모두 `NNG`이다. **형태소 분석기만으로는 雪/目을 구별할 수 없다.** → Gemini가 필요한 이유

### 3-2. Gemini로 문맥 판별
**설계**
- 후보 의미를 **사전(`data/lexicon.json`)에서 골라 주고** 그중에서만 선택하게 했다. → 사전에 없는 답(환각)을 막는다.
- `temperature=0`으로 매번 같은 답이 나오게 했다. 답은 JSON 형식으로 받아 자동으로 채점했다.
- 문장 12개를 **한 번의 요청으로 묶어서** 물었다. 이유는 3-4절에 있다.
- 받은 답의 원문과 근거는 `outputs/gemini_cache.json`의 `_원본_응답`에 저장했다. 다시 실행해도 같은 답을 쓰고, 판단 근거를 나중에 확인할 수 있다.

**결과: 기본 문장 12개(25개 단어)** (`outputs/disambiguation.md`)

| 방법 | 의미 정확도 | 장단 정확도 |
|---|---|---|
| baseline (항상 첫 번째, 즉 짧은 의미) | 56% (14/25) | 60% (15/25) |
| Gemini (`gemini-3.6-flash`) | **100% (25/25)** | **100% (25/25)** |

- Gemini가 틀린 문장: **없음**
- 인상적인 근거
  - "올해 첫눈은 **눈이 부시게** 하얗게 내렸다" → 目: "하얗게 내린 눈으로 인해 부심을 느끼는 신체 기관"
    - 옆에 '하얗게 내렸다'라는 雪 단서가 있는데도, '부시다'와의 관계로 目을 골랐다.
  - "이 배는 저 배보다 두 **배**나 크다" → 倍: "크기의 수량적 곱절(두 배)"
  - "아버지와 아들, 두 **부자**는 마침내 **부자**가 되었다" → 앞은 父子("앞서 언급된 아버지와 아들"), 뒤는 富者
- baseline은 정답이 장음인 11개 중 10개를 틀렸다. 맞힌 1개는 사전에 의미가 하나뿐인 '눈보라'다.
- **의미는 틀렸는데 장단은 맞은 경우가 baseline에서 1건** 있었다.
  - "올해 **첫눈**은 ..."의 '눈'은 정답이 雪인데 baseline은 目을 골랐다(의미 X).
  - 그런데 이 '눈'은 단어 중간이라 雪이어도 짧게 읽는다(장단 O).
  - 그래서 baseline의 장단 정확도(60%)가 의미 정확도(56%)보다 높다.
  - **"의미를 틀려도 소리는 맞을 수 있다."** → 장단음 문제에서는 두 정확도를 따로 재야 한다.

### 3-3. 어려운 문장으로 다시 시험 (100%를 의심해 보기)
기본 문장은 '타고', '쏘였다'처럼 의미를 알려 주는 단서가 바로 옆에 있다. 그래서 단서가 약하거나 헷갈리게 만든 12문장(20개 단어)을 따로 만들었다(`data/sentences_hard.json`).

| 함정 유형 | 예시 |
|---|---|
| 관용 표현을 알아야 함 | 벌을 **치다**(벌을 기르다), 발을 **걷다**(가림막을 말아 올리다) |
| 같은 구조의 반복 | 경마장에서 그는 **내 말**은 듣지도 않고 **자기 말**만 응원했다 |
| 숫자 단서 없는 곱절 | 쌀값이 **배로** 올랐다 |
| 반대 의미로 끌어당기는 단서 | **함박눈**이 내린 날, 그는 **눈**을 감고 소원을 빌었다 → 目 |
| 추론이 필요함 | 그 집 **부자**는 얼굴이 꼭 닮았다 → '닮았다'에는 두 사람이 필요 → 父子 |

| 방법 | 의미 정확도 | 장단 정확도 |
|---|---|---|
| baseline | 45% (9/20) | 55% (11/20) |
| Gemini (`gemini-3.6-flash`) | **100% (20/20)** | **100% (20/20)** |

- Gemini가 틀린 문장: **없음.** 함정을 넣은 20개도 모두 맞혔다.
- 함정을 어떻게 풀었나 (Gemini가 댄 근거)
  - **벌을 치는** 일 → 蜂: "꿀을 얻거나 기르기 위해 치는 곤충". '벌을 치다'라는 관용 표현을 알았다.
  - **발을 걷고** → 簾: "햇빛을 가리기 위해 쳐 놓은 가림막". '걷다'를 walk가 아니라 '말아 올리다'로 이해했다.
  - 쌀값이 **배로** 올랐다 → 倍: "가격이 두 배로 늘어났음을 나타내는 곱절". 숫자 단서 없이도 맞혔다.
  - 그 집 **부자**는 얼굴이 꼭 닮았다 → 父子: "얼굴이 닮았다는 문맥에서 아버지와 아들 관계"
  - **함박눈**이 내린 날, 그는 **눈**을 감고 → 目: "소원을 빌 때 감는 신체 기관". 앞의 雪 단서에 끌려가지 않았다.
- baseline은 기본 문장보다 더 떨어졌다(의미 56% → 45%). 정답이 장음인 9개는 하나도 맞히지 못했다.
- baseline에서 **의미는 틀렸는데 장단은 맞은 경우가 2건** 있었다.
  - "**배**가 고픈 선원은 배 위에서 **배**를 깎아 먹었다"의 배/腹과 배/梨를 모두 배/舟로 골랐다.
  - 셋 다 짧은 소리라 장단은 맞았다. 장단음만 보면 의미를 완벽히 몰라도 되는 경우가 있다.
- 해석
  - 사람이 읽어서 정답을 하나로 정할 수 있는 문장이라면, 함정을 넣어도 Gemini는 문맥으로 풀어냈다.
  - 반대로 **사람도 정답을 정할 수 없는 문장**(예: "어제 본 **눈**이 아직도 생각난다")은 정답이 없어서 정확도를 잴 수 없다. 이것은 문맥 판별 방식의 근본적인 한계다(7절).

### 3-4. 시행착오 기록 (문제 해결 과정)
| 문제 | 원인 | 해결 |
|---|---|---|
| `404 NOT_FOUND` | 처음 쓴 `gemini-2.5-flash`가 신규 사용자에게 더 이상 제공되지 않음 | 오류 메시지가 권한 모델로 교체했다. 노트북에서 **쓸 수 있는 모델 목록을 조회해 고르도록** 바꿨다 |
| 모델을 바꿔도 `503 UNAVAILABLE`이 반복됨 | 무료 등급 요청은 서버가 붐빌 때 먼저 거절된다. 12문장을 12번 따로 요청해서 한 번만 거절돼도 실패했다 | ① 잠시 기다렸다 자동 재시도 ② **12문장을 한 번의 요청으로 묶음** ③ 짧은 시험('안녕')은 성공하는데 실험만 실패해서, 두 요청의 차이(JSON 응답 모드)를 없앰 → `gemini-3.6-flash`로 성공 |
| 실패하면 원인과 무관한 `FileNotFoundError`만 보임 | 결과 파일을 모든 단계가 끝난 뒤에만 썼다 | 단계마다 결과를 저장하고, 실패하면 원인과 해결 방법을 결과 파일에 남겼다 |
| Google Cloud TTS `403 Forbidden` | 가지고 있던 키로는 Cloud Text-to-Speech를 쓸 수 없었다(API가 켜져 있지 않거나 결제 미등록) | 실패하면 **gTTS + 철자 변형**으로 자동 전환하게 했다. 오류 메시지에 API 키가 찍히지 않도록 키 전송 방식도 바꿨다 |

- 배운 점: 외부 API는 **모델 이름이 바뀌고, 서버가 붐비고, 권한이 막힐 수 있다.** 그래서 다음 세 가지가 중요했다.
  - 결과를 저장해 두고 다시 묻지 않기
  - 요청 횟수를 줄이기
  - 실패 원인이 바로 보이게 만들기

### 3-5. 상용 TTS에 적용: gTTS + 철자 변형
**방법**
- 상용 TTS는 모델 내부를 열어 볼 수 없다. 그래서 바꿀 수 있는 것은 **입력 글자뿐**이다.
- 처음에는 Google Cloud TTS의 SSML(`<prosody rate="55%">눈</prosody>`)로 장음 음절만 느리게 읽히려 했다. 하지만 403 오류로 쓸 수 없었다.
- 그래서 무료 TTS인 **gTTS(구글 번역 음성)** 를 쓰고, 장음 음절의 **모음을 한 번 더 적는 철자 변형**을 했다(`src/approach1_commercial.py`의 `lengthen_syllable`).
  - 받침이 있으면 받침을 뒤 음절로 옮긴다: 눈 → 누 + 운 = **누운**
  - 이중모음은 뒤쪽 단모음을 늘린다: 과(ㅘ = ㅗ + ㅏ) → 과아

**Gemini 판별 결과를 반영한 실제 입력** (장음으로 판별된 음절만 바뀜)

| 원래 문장 | gTTS에 넣은 문장 |
|---|---|
| 눈에 눈이 들어가서 눈물이 났다. | 눈에 **누운**이 들어가서 눈물이 났다. |
| 그는 말을 타고 달리면서 계속 말을 걸었다. | 그는 말을 타고 달리면서 계속 **마알**을 걸었다. |
| 밤에 먹는 밤은 유난히 달다. | 밤에 먹는 **바암**은 유난히 달다. |
| 사과를 깎다가 친구에게 사과했다. | 사과를 깎다가 친구에게 **사아과**했다. |

- 짧은 소리인 目·馬·夜·沙果 쪽 단어는 그대로 두었다. 그래서 같은 문장 안에서 짧은 소리와 긴 소리가 비교된다.
- 표준 발음법 제6항 때문에 '눈물'의 '눈'처럼 단어 중간 음절은 바꾸지 않았다.

**청취 결과 (직접 듣고 느낀 점)**
- **'사과' 문장을 빼면, 철자로 인위적으로 늘린 음성이 훨씬 자연스러웠다.**
- 모델을 바꾸지 않고 **입력 글자를 조금씩 바꾸는 것만으로도** 장음을 자연스럽게 표현할 수 있었다.
- '사과'만 어색했던 이유 (가설: 멜 스펙트로그램으로 확인해 볼 것)
  - 눈·말·밤은 **한 음절 단어**다. 그래서 '누운'이 한 음절이 길어진 것처럼 들릴 수 있다.
  - '사과'는 **두 음절 단어**다. '사아과'가 되면 세 음절 단어처럼 리듬이 바뀌고, 뒤의 '했다'까지 붙어 '사아과했다'가 된다.
  - 확인 결과 (5-5절): **가설을 뒷받침한다.**
  - 한 음절 단어(눈·말·밤)는 늘어난 곳이 **한 군데**였고, 문장이 0.085~0.107초 길어졌다.
  - '사과'는 늘어난 곳이 **두 군데**로 나뉘었고, 문장이 0.235초나 길어졌다. 한 음절 단어의 2~3배다.
  - 즉 '사아과'는 모음 하나가 길어진 것이 아니라, **음절이 하나 더 생긴 것처럼** 단어 전체의 리듬이 바뀌었다.

**한계**
- 철자 변형은 '모음을 하나 더 읽게' 하는 방식이다. 그래서 늘어나는 길이를 정확히 정할 수 없다. 얼마나 늘어날지는 TTS가 결정한다.
- 단어의 음절 수가 많을수록 리듬이 바뀌어 어색해질 수 있다('사과' 사례).

## 4. 방법 2: VITS 텐서에 직접 개입

### 4-1. 아이디어
```python
def hook(module, inputs, output):          # output = log_duration, 모양 (1, 1, 토큰 수)
    return output + log_w                  # 장음 모음 토큰 위치만 log(w), 나머지는 0
model.duration_predictor.register_forward_hook(hook)
```
- **왜 log 공간에서 더하나?**
  - 모델은 `duration = ceil(exp(log_duration))`로 프레임 수를 계산한다.
  - `exp(a + log w) = w · exp(a)`이므로, 더하기 한 번이 곱하기 w가 된다.
- **왜 speaking_rate를 쓰지 않았나?** speaking_rate는 문장 전체의 속도를 바꾼다. 우리는 모음 하나만 늘려야 한다.
- **왜 blank 토큰도 늘렸나?**
  - MMS 토크나이저는 글자 사이에 blank(`_`)를 끼운다(`_ n _ u _ n _`).
  - 모음 소리가 blank 쪽까지 이어지는 경우가 많아서, 모음 토큰과 바로 뒤 blank를 같이 늘렸다.
  - 실험해 볼 것: 모음 토큰만 늘렸을 때와 비교 ( )
- **공정한 비교**: VITS의 duration predictor는 난수를 쓴다. 그래서 기본 음성과 수정 음성을 같은 seed로 생성했다.
- **입력이 로마자인 이유**
  - `facebook/mms-tts-kor`는 한글을 uroman으로 로마자화한 입력으로 학습됐다.
  - 그래서 한 음절씩 로마자로 바꾸면서 "이 로마자 글자는 몇 번째 한글 음절에서 왔는지"를 기록해 두었다(`romanize`).
- 참고: 실행 결과에서 blank 토큰이 `'u'`로 표시됐다. MMS 한국어 모델의 사전에서 0번 토큰이 `u`이기 때문이다. 토크나이저는 0번 토큰을 blank로 끼워 넣으므로 실제로는 blank 역할이다.
- **사전 검증** (학습되지 않은 VITS로 hook 동작만 확인, `tests/test_vits_hook.py`)
  - 지정한 토큰만 3→6, 10→19 프레임으로 늘었다.
  - 나머지 토큰은 그대로였다.
  - 음성 길이는 늘어난 프레임 수 × 256 샘플만큼 정확히 늘었다.

## 5. 멜 스펙트로그램: 어떻게 그렸나

### 5-1. 멜 스펙트로그램이란?
- 소리를 **시간(가로) × 주파수(세로) × 세기(색)** 의 그림으로 바꾼 것이다.
- 모음을 발음하면 특정 주파수 대역에 에너지가 몰린다. 이것이 **포먼트**이고, 그림에서 **가로 줄무늬(띠)** 로 보인다.
- 그래서 장음이 제대로 되었다면 **그 모음의 띠가 옆으로 더 길게 이어져야** 한다. 이것이 그림에서 확인할 핵심이다.

### 5-2. 만드는 원리 (단계별)
| 단계 | 하는 일 | 이 탐구에서 쓴 값 | 이유 |
|---|---|---|---|
| ① 샘플링 맞추기 | 음성을 같은 샘플링 주파수로 바꾼다(리샘플링) | 16,000Hz | gTTS와 VITS의 원래 주파수가 달라도 같은 기준으로 비교하려고. VITS 원래 값과 같다 |
| ② 무음 제거 | 앞뒤의 조용한 부분을 자른다 | 최대 음량보다 35dB 작으면 무음 | gTTS는 앞뒤 무음 길이가 매번 달라 길이 비교를 방해한다 |
| ③ 짧게 자르기(STFT) | 음성을 짧은 조각(창)으로 잘라 조금씩 밀면서 조각마다 푸리에 변환을 한다 | 창 1024샘플(64ms), 이동 256샘플(16ms) | 소리는 계속 변하므로 "그 순간"의 주파수 성분을 보려고. 16ms마다 한 칸 = 그림의 가로 한 칸 |
| ④ 세기 구하기 | 주파수 성분의 크기를 제곱해 에너지(파워)로 만든다 | | |
| ⑤ 멜 척도로 묶기 | 주파수 축을 80개 구간(멜 필터)으로 묶는다. 낮은 주파수는 촘촘하게, 높은 주파수는 넓게 묶는다 | 80개, 0~8,000Hz | 사람 귀는 낮은 주파수의 차이에 더 민감하다. librosa 기본값은 약 1,000Hz까지는 일정 간격, 그 위로는 로그 간격이다 |
| ⑥ 데시벨(dB)로 바꾸기 | `10 × log10(에너지 / 최댓값)` | 가장 센 곳 = 0dB, 나머지는 음수 | 사람 귀는 소리 크기를 로그로 느낀다. 작은 소리도 그림에서 보이게 하려고 |
| ⑦ 그리기 | 두 음성을 위아래로 놓고 **같은 시간 눈금**을 쓴다 | 위: 기본, 가운데: 장음 반영 | 같은 눈금이어야 길이 차이가 눈으로 보인다 |

- VITS는 원래 16,000Hz이고, 프레임 하나가 256샘플이다. 그림의 가로 한 칸(256샘플)과 VITS의 duration 프레임 한 칸이 **정확히 일치**한다.
  - 그래서 duration을 누적해 더하면 장음 음절이 몇 초부터 몇 초까지인지 정확히 계산된다.
  - 이 구간을 그림에 **하늘색**으로 표시했다.
- 상용 TTS는 이런 정렬 정보가 없다. 그래서 다음의 DTW로 어디가 늘어났는지 추정했다.

### 5-3. DTW로 "어디가 늘어났는지" 추정하기
- DTW(동적 시간 정렬)는 길이가 다른 두 음성에서 **서로 같은 소리끼리 짝을 지어 주는** 방법이다.
- 기본 음성의 한 칸이 수정 음성의 몇 칸과 짝지어졌는지 세면, 그 순간이 **몇 배로 늘어났는지** 알 수 있다.
  - 예: 1칸이 2칸과 짝지어졌으면 2배로 늘어난 것이다.
- 그림 맨 아래 주황색 곡선이 이 배율이다. 1보다 크게 솟은 곳이 늘어난 부분이다.
- 검증: 합성 신호에서 한 구간만 2배로 늘렸을 때, 그 구간의 평균 배율은 2.07, 나머지는 0.98이었다.
- 주의: 소리가 일정한 구간 안에서는 늘어난 위치가 한쪽에 몰려서 표시된다. 그래서 곡선의 모양보다 **구간 평균**으로 해석해야 한다.

### 5-4. 코드 (`src/analysis.py`)
```python
SR, N_FFT, HOP, N_MELS = 16000, 1024, 256, 80   # 16kHz, 창 64ms, 이동 16ms, 멜 구간 80개

def mel_db(wav, sr):
    if sr != SR:                                              # ① 샘플링 맞추기
        wav = librosa.resample(wav, orig_sr=sr, target_sr=SR)
    mel = librosa.feature.melspectrogram(                     # ③ STFT → ④ 파워 → ⑤ 멜 필터 80개
        y=wav, sr=SR, n_fft=N_FFT, hop_length=HOP, n_mels=N_MELS)
    return librosa.power_to_db(mel, ref=np.max)               # ⑥ dB로 (가장 센 곳 = 0dB)

def trim(wav, top_db=35):                                     # ② 앞뒤 무음 제거
    return librosa.effects.trim(wav, top_db=top_db)[0]

def dtw_stretch(base, mod, smooth=5):                         # 5-3. DTW 늘어남 배율
    a, b = mel_db(base, SR), mel_db(mod, SR)
    a = (a - a.mean(1, keepdims=True)) / (a.std(1, keepdims=True) + 1e-6)   # 멜 구간마다 표준화
    b = (b - b.mean(1, keepdims=True)) / (b.std(1, keepdims=True) + 1e-6)
    _, path = librosa.sequence.dtw(X=a, Y=b, metric="euclidean")           # 같은 소리끼리 짝짓기
    counts = np.bincount(path[:, 0], minlength=a.shape[1])                  # 기본 1칸 ↔ 수정 몇 칸?
    ratio = np.convolve(counts, np.ones(smooth) / smooth, mode="same")      # 5칸 이동 평균으로 매끄럽게
    times = np.arange(a.shape[1]) * HOP / SR                                # 칸 번호 → 초
    return times, ratio
```

    - 그래서 **장음 구간 안의 봉우리만** 의미 있는 결과로 봤다.

## 6. 두 방법 비교와 결론
| | 방법 1: 입력 변경 (gTTS + 철자) | 방법 2: 텐서 개입 (VITS) |
|---|---|---|
| 개입 지점 | 모델 바깥(입력 글자) | 모델 안(duration 텐서) |
| 제어 정밀도 | 낮음. 얼마나 늘어날지는 TTS가 정한다 | 높음. 지정한 토큰의 프레임 수만 정확히 늘어났다 |
| 실제로 늘어난 길이 | 0.085~0.107초 (사과는 0.235초) | 0.032~0.064초 |
| 정렬 정보 | 없음 → DTW로 추정 | duration으로 정확히 앎 |
| 적용 범위 | 어떤 TTS든 가능 | 내부에 접근할 수 있는 모델만 |
| 음질 | 기본 발음이 좋다 | 기계음이 심하고 발음이 뭉개지는 경우가 많다 |
| 자연스러움 | 두 음절 단어('사과')를 늘리면 조금 부자연스럽다. 나머지는 자연스럽다 | 1.75~2.0배가 가장 잘 들렸다. 더 크게 하면 인위적이다 |
| **내 판단** | **더 자연스러웠다** | 원리는 정확하지만 결과는 덜 자연스러웠다 |

**결론**
- 직접 들어 보니 **gTTS + 철자 변형 쪽이 더 자연스러웠다.**
  - gTTS는 기본 발음이 좋아서, 입력을 조금 바꾸는 것만으로도 자연스러운 장음이 나왔다.
  - VITS는 기본 음질이 낮아서, 장음을 정확히 넣어도 전체적으로 어색했다.
- 흥미로운 점은 **정밀하게 제어할 수 있는 방법(VITS)은 음질이 낮고, 음질이 좋은 방법(gTTS)은 제어가 거칠다**는 것이다.
  - VITS는 원하는 모음 하나의 길이를 프레임 단위로 정확히 바꿀 수 있었다.
  - 하지만 그 모음에 원래 배정된 시간이 2프레임(32ms)처럼 짧으면, 몇 배를 곱해도 귀에 띄게 길어지지 않았다.
- 그래서 가장 좋은 조합은 **음질 좋은 한국어 전용 모델의 내부(duration)에 직접 개입하는 것**이라고 생각한다.
  - 또는 곱하기 대신 "장음 모음은 최소 몇 프레임" 같은 **최소 길이**를 정하는 방식이 더 나을 수 있다(7절).

## 7. 한계와 후속 탐구
- 사전에 있는 단어만 처리한다. → 표준국어대사전 전체에서 장단음 동음이의어를 자동으로 추출할 수 있을까?
- 문맥만으로는 정답이 하나로 정해지지 않는 문장(예: "어제 본 눈이 아직도 생각난다")이 있다.
  - 앞뒤 문장까지 함께 보거나, 정할 수 없을 때 어떻게 읽을지 정하는 규칙이 필요하다.
- 평가 문장이 45개 단어뿐이다. 기본 25개와 어려운 20개를 모두 맞혔지만, 더 많은 문장으로 시험해야 일반적인 성능을 말할 수 있다.
- 철자 변형은 단어의 음절 수가 많을수록 리듬이 바뀌어 어색해질 수 있다('사과' 사례).
- VITS는 모음에 배정된 프레임이 원래 적으면(2프레임 = 32ms) 곱하기로는 거의 늘어나지 않는다.
  - 개선안: 곱하기 대신 **최소 길이**를 정한다(예: 장음 모음은 적어도 8프레임 = 128ms).
- MMS 한국어 모델은 철자 기반 로마자(uroman)를 입력으로 받는다. 그래서 '깎다가'[깍따가]처럼 철자와 발음이 다른 단어를 잘 발음하지 못했다.
  - 개선안: 한국어 전용 TTS 모델이나 발음 기호(음소)를 입력으로 받는 모델을 쓴다.
- 용언의 장단(감ː다/감다, 묻ː다/묻다)과 활용할 때 짧아지는 현상(감ː다 → 감아[가마])은 다루지 못했다.
- 길이만 바꿨다. 실제 장음에는 음높이나 강세 변화가 함께 나타날 수 있다.
- 평가가 내 귀와 구간 길이뿐이다. → 여러 사람에게 들려주고 "어느 쪽이 雪으로 들리나" 청취 실험을 할 수 있다.
- 근본적인 해결: 장단 표시(ː)를 입력에 넣은 데이터로 TTS를 학습시키는 방법

## 면접 예상 질문 (내 말로 답해 보기)
1. **형태소 분석기만으로는 왜 안 되나?**
   → 품사까지 같은 동음이의어는 구별하지 못한다('눈/NNG'). 문맥 이해는 LLM이 맡았다.
2. **Gemini가 틀리면 어떻게 하나?**
   → 후보를 사전 안으로 제한하고, 정답 데이터로 정확도를 쟀다. 기본 문장에서 100%가 나와서 오히려 의심이 들었다. 그래서 함정을 넣은 어려운 문장으로 다시 시험했고, 그것도 100%였다(3-3절).
3. **API가 안 될 때 어떻게 했나?**
   → 404는 모델 교체, 503은 재시도와 요청 묶기, 403은 다른 TTS로 자동 전환했다(3-4절).
4. **상용 TTS는 내부를 못 바꾸는데 어떻게 장음을 만들었나?**
   → 입력 철자를 바꿨다(눈 → 누운). 한 음절 단어는 자연스러웠지만 두 음절인 '사과'는 어색했다(3-5절).
5. **텐서에 개입했다는 게 구체적으로 무슨 뜻인가?**
   → duration predictor의 출력에 hook을 걸고, 장음 모음 토큰의 log_duration에 log(w)를 더했다.
6. **왜 곱하지 않고 더했나?** → 4-1절
7. **장음이 제대로 됐는지 어떻게 확인했나?**
   → duration 프레임 수, 멜 스펙트로그램의 포먼트 띠 길이, DTW 배율, 직접 청취(5절)
8. **멜 스펙트로그램은 어떻게 만드나?**
   → 16kHz로 맞추고, 64ms 창을 16ms씩 밀며 푸리에 변환하고, 80개 멜 구간으로 묶은 뒤 dB로 바꾼다(5-2절).
9. **두 방법 중 무엇이 더 나은가?**
   → 직접 들어 보니 gTTS + 철자 변형이 더 자연스러웠다. VITS는 원하는 모음만 정확히 늘렸지만 기본 음질이 낮았다. 정밀한 제어와 좋은 음질을 함께 얻으려면, 음질 좋은 한국어 전용 모델의 duration에 개입해야 한다(6절).
10. **VITS에서 1.8배로 늘렸는데 왜 1.8배만큼 길어지지 않았나?**
   → 모음과 바로 뒤 blank만 늘렸고(1.67배), 음절의 자음은 그대로라 음절 전체는 1.27배였다. 게다가 모음에 원래 2프레임밖에 없어서 늘어난 절대 길이가 작았다(4-2절).
11. **다시 한다면 무엇을 바꾸겠나?** → 곱하기 대신 최소 길이 방식, 또는 한국어 전용 모델 사용(7절)
